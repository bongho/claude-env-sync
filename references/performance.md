# 성능 규칙 (Performance & Context Rules)

## 모델 선택 전략

### Opus (복잡/고품질)
- 시스템 아키텍처 설계
- 보안 취약점 심층 분석
- 복잡한 리팩토링 계획
- AI/ML 전략 수립
- 코드 리뷰 (핵심 모듈)

### Sonnet (밸런스)
- 코드 구현 및 테스트
- 빌드 에러 해결
- 데이터 분석 및 시각화
- 일반 코드 리뷰
- E2E 테스트 작성/실행
- 실험 추적 및 모델 평가

### Haiku (빠른/경량)
- 문서-코드 동기화
- 단순 포맷팅 작업
- 파일 목록 조회
- 간단한 질의응답
- 로그 분석

### Advisor 패턴 (동적 에스컬레이션) — 권장 기본 전략

> 사전 분류(pre-classification) 라우팅보다 런타임 에스컬레이션이 구조적으로 우월

**패턴**: Sonnet(executor) → 막히면 → Opus(advisor) 동적 개입

```
# API 사용 시 (클라이언트 앱 개발):
tools=[{"type": "advisor_20260301", "name": "advisor",
        "model": "claude-opus-4-6", "max_uses": 3}]

# Claude Code 세션 / 에이전트 위임 시:
- executor: Sonnet 에이전트 (도구 호출, 반복 처리)
- advisor: Opus 서브에이전트 (판단 필요 시에만, max_uses=2~3)
- advisor는 도구 호출 없이 executor에게 계획/수정안만 전달
```

**언제 Advisor를 활성화할 것인가:**
| 작업 유형 | 전략 |
|---------|------|
| 복잡한 아키텍처 판단, 연구 맥락 연결, 보안 분석 | Sonnet + Opus advisor (max_uses=2) |
| 코드 구현, 데이터 분석, 포맷팅 | Sonnet 단독 |
| 파일 조회, 링크 검증, 단순 태그 검사 | Haiku 단독 |

**벤치마크** (Anthropic 공식):
- Sonnet + Opus advisor: SWE-bench 2.7% 향상 + 11.9% 비용 절감
- Haiku + Opus advisor: BrowseComp 19.7%→41.2%, Sonnet 단독 대비 비용 85% 절감

> 출처: [The Advisor Strategy](https://claude.com/blog/the-advisor-strategy) (2026)

## 컨텍스트 윈도우 관리

### 핵심 원칙: Signal-to-Noise Ratio
- **모든 토큰 결정의 기준**: "이 토큰이 원하는 결과를 얻을 확률을 높이는가?"
- 컨텍스트 rot: 토큰 증가 시 **점진적 성능 저하** (절벽이 아님, n² 관계 처리 부담)
- 컨텍스트는 희소한 자원 — 더 나은 모델도 이 기본 제약을 해결하지 못함

### Progressive Disclosure 3단계
- **Level 1**: 메타데이터만 로드 (name + description) → 사용 여부 판단
- **Level 2**: 관련성 감지 시 전체 문서/SKILL.md 로드
- **Level 3**: 필요한 보조 파일만 동적 읽기
- 적용: CLAUDE.md/rules도 "목차 → 특정 장 → 부록" 구조 유지

### 컨텍스트 절약 원칙
- 대량 파일 탐색: `Task(Explore)` 에이전트 사용 (메인 컨텍스트 절약)
- 파일 읽기: 필요한 부분만 `offset`/`limit` 사용
- 검색: `Grep` > `Bash grep` (최적화된 출력)
- 반복 작업: `Task` 에이전트에 위임
- **Just-in-Time Retrieval**: 모든 데이터 사전 로드 대신 경량 식별자(파일 경로, 링크)로 런타임에 동적 로드
- **Tool Result Cleanup**: 메시지 히스토리 깊숙이 있는 도구 결과 제거 (호출 자체는 유지), 장기 세션에 유효

### 컨텍스트 압축 3단계 전략 (장기 세션)

```
1단계: 도구 결과 프루닝
  - 오래된 도구 결과 콘텐츠 → 짧은 플레이스홀더로 교체
  - 대화 의미 유지, 불필요한 토큰 오버헤드 제거

2단계: 경계 보호
  - 처음 N개 메시지 보호 (시스템 프롬프트 + 초기 교환)
  - 마지막 부분: 토큰 예산 기반 동적 보호 (~20% 할당)

3단계: 구조화된 축약
  - /compact 전략의 템플릿으로 요약
  - 반복 압축 시 이전 요약을 재생성하지 않고 업데이트만
```

> **언제 쓸까**: 세션이 길어져 응답 품질이 떨어지는 신호 감지 시 (느린 응답, 앞 내용 망각, 반복 질문)

### /compact 전략
- 긴 대화 시 주기적으로 `/compact` 고려
- compact 전 핵심 결정사항/컨텍스트 정리
- 실험 결과, 아키텍처 결정 등 보존 필요 정보 명시

**구조화된 축약 템플릿** (compact 요청 시 아래 형식으로 요약 지시):
```
Goal: 이 대화에서 달성하려는 목표
Progress: 현재까지 완료된 내용
Decisions: 내린 주요 결정 및 그 이유
Resolved: 해결된 질문/이슈
Pending: 아직 미결인 질문/이슈
Remaining: 남은 작업 목록
```
> 핵심 지시: "대화 질문에 응답하지 말고, 다음 작업을 위한 배경 정보만 제공하라"
> 반복 compact 시 이전 요약을 재생성하지 않고 Remaining → 업데이트만 수행

**압축 임계값**: 컨텍스트 창 85% 도달 시 고려, 실패 시 600초 후 재시도

### MCP 서버 관리
- 활성 MCP 서버: **10개 이내** 유지
- 사용하지 않는 MCP 비활성화
- MCP 응답 크기 모니터링

### 컨텍스트 안티패턴
- 프롬프트에 복잡한 if-else 로직 하드코딩 (취약성 증가)
- 모든 엣지 케이스 나열 → **대표적 few-shot 예시**가 더 효과적
- 동적으로 변경되는 콘텐츠에 정적 색인 사용
- 에이전트 없이 모든 데이터를 사전 로드

## 응답 최적화
- 대용량 출력: 파일 저장 후 경로 제공 (스크래치패드 활용)
- 테이블/리스트: 10개 이상 시 요약 + 상세 파일 분리
- 코드 블록: 변경 부분만 표시, 전체 파일 출력 최소화

## 에이전트 성능 최적화
- 독립 작업 병렬 실행
- 에이전트 최대 턴수 적절 설정
- 불필요한 에이전트 호출 방지 (단순 작업은 직접 처리)

## 비용 의식
- BigQuery: 파티션 프루닝, 필요 컬럼만 SELECT
- API 호출: 캐싱, 배치 처리
- 모델 학습: spot/preemptible 인스턴스 우선
- 불필요한 에이전트 중첩 호출 방지
